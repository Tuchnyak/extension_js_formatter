## 0. Правила работы для агента (читать первым)

1. **Работаем строго по шагам.** Один шаг — одна сессия работы. После завершения шага **остановись** и выведи:
   - что сделано (кратко);
   - результат `npm run compile` и `npx biome check .`;
   - чек-лист ручной проверки из раздела «Проверка» этого шага.
   Не начинай следующий шаг без явного подтверждения владельца.
2. **Каждый шаг достраивает предыдущий, а не переписывает его.** Если для шага нужно существенно менять код прошлых шагов — остановись и объясни почему, прежде чем менять.
3. **Если спецификация расходится с реальностью** (API WXT/Chrome работает не так, как описано; команда не существует; решение требует нового permission) — остановись и спроси. Не импровизируй молча.
4. **Сверяйся с актуальной документацией WXT (wxt.dev).** API менялся между версиями: например, в 0.20.x удалён экспорт `wxt/sandbox`. Не используй импорты из старых туториалов; `defineBackground`, `defineContentScript`, `browser` в WXT доступны через auto-imports.
5. **Каждый шаг делается в отдельной ветке `feature/<name>`** (например, `feature/v1-step-3`). В конце шага — коммит с сообщением вида `v1 step 3: collapsible tree and themes`, затем остановка на проверку. После подтверждения владельца ветка сливается в `master` (`git merge --no-ff`). Пуш в удалённый репозиторий делает владелец. Коммиты без подписи `Co-Authored-By`. См. раздел 8.
6. **Язык:** весь UI — на английском. Комментарии в коде — на английском. Отчёты владельцу — на русском.

## 1. Продукт и жёсткие принципы

**Что это:** расширение, которое красиво и безопасно показывает JSON: автоматически на JSON-страницах, из вставленного вручную текста и из выделенного на любой странице фрагмента.

**Непреложные ограничения (нарушение = баг):**

- **Ноль сетевых запросов.** Никаких `fetch`, аналитики, телеметрии, шрифтов/скриптов с CDN, remote config. Всё работает офлайн.
- **Ноль runtime-зависимостей.** Парсинг — нативный `JSON.parse`, рендер и подсветка — собственный код. Dev-зависимости (WXT, TypeScript, Biome, позже Vitest) допустимы.
- **Минимальные permissions:** только `contextMenus`, `storage` и host-доступ для content script (см. раздел 3.4). Любой новый permission — только после согласования.
- **Никакого `innerHTML` с данными пользователя.** DOM строится через `createElement` / `textContent`. Ссылки — только схемы `http:` / `https:`, с `rel="noopener noreferrer"` и `target="_blank"`.
- **Никаких аккаунтов, никакого хранения пользовательских данных** кроме настроек (тема, переключатель автоформата, см. Шаг 5) и временной передачи выделенного текста.

## 3. Архитектура

### 3.1. Структура проекта

```
src/                   # весь код расширения (srcDir в wxt.config.ts), см. раздел 8
  entrypoints/
    background.ts      # context menu, click on toolbar icon
    content.ts         # auto-format JSON documents
    viewer/            # unlisted page: viewer + manual paste (собирается как viewer.html)
      index.html
      main.ts          # viewer page logic
      style.css        # styles of the viewer page itself
  lib/
    parse.ts           # JSON.parse wrapper + error location (line/column)
    render.ts          # value -> DOM tree (shared by viewer and content script)
    toolbar.ts         # raw/parsed toggle, expand/collapse all, theme switch
    theme.ts           # theme state: system | light | dark, persisted
    styles.css         # shared styles, CSS custom properties, all classes prefixed `jv-`
  public/icon/         # extension icons (publicDir в wxt.config.ts)
fixtures/              # sample JSON files for manual testing
store/                 # store listing drafts (step 6)
```

Если конвенции WXT требуют иного расположения файлов (например, `entrypoints/viewer/index.html`) — следуй WXT, сохраняя разделение ответственности.

### 3.2. Общее ядро

**Ключевой принцип: один движок рендера, три точки входа.** `lib/parse.ts` + `lib/render.ts` + `lib/toolbar.ts` + `lib/styles.css` используются и в viewer-странице, и в content script без дублирования.

`lib/parse.ts`:
- `parseJson(text: string): { ok: true; value: unknown } | { ok: false; message: string; line?: number; column?: number }`.
- Позицию ошибки вычислять **самостоятельно** из смещения в сообщении `SyntaxError` (формат сообщений V8 может меняться — извлечь `position N`, если есть, и пересчитать в line/column по исходному тексту). Если позиция не найдена — вернуть только `message`. **Отклонение (раздел 8, п. 2):** если позиции нет в сообщении, она находится запасным строгим сканером JSON; «только `message`» остаётся лишь на случай, когда не помог и он.

`lib/render.ts`:
- `renderJson(value: unknown): HTMLElement` — рекурсивный обход.
- Константа `MAX_RENDER_BYTES = 10 * 1024 * 1024`. Если исходный текст больше — дерево **не строить**, показать raw-текст и уведомление «Too large to format (N MB). Showing raw.»

### 3.3. Три точки входа

1. **Прямая навигация на JSON-URL** → `content.ts` подменяет содержимое страницы отформатированным деревом.
2. **Клик по иконке расширения** → `background.ts` открывает `viewer.html` в новой вкладке (без popup: popup закрывается при потере фокуса, для просмотра неудобно). Для работы `action.onClicked` в манифест нужно явно добавить `action: {}` через `wxt.config.ts`.
3. **Выделение + контекстное меню** → `background.ts` кладёт текст в `storage.session` и открывает `viewer.html?id=<key>`; viewer читает значение, **сразу удаляет его** из storage и форматирует.

### 3.4. Permissions (итоговые для v1)

- `contextMenus` — пункт меню на выделенном тексте.
- `storage` — `storage.session` для передачи выделения; `storage.local` для темы и переключателя автоформата.
- Host-доступ для content script: `matches: ["<all_urls>"]`. **Это неизбежно** для автоформата на любом JSON-URL, и Chrome покажет пользователю предупреждение «Read and change all your data on all websites». Компенсация — content script мгновенно выходит на не-JSON страницах и ничего не читает/не отправляет (см. шаг 5), и это явно пишется в описании стора.

## 6. Релиз v2.0.0 — JSON → SQL INSERT (generic)

Без привязки к конкретной СУБД. Генерация стандартного SQL.

### Шаг 2-1 — Модуль конвертации + тесты

**Сделать:**
- Подключить Vitest (`npm run test`).
- `lib/sql.ts`: чистая функция `jsonToInsert(value, options): { ok: true; sql: string } | { ok: false; reason: string }`.
- Опции: `tableName: string`, `mode: "multi-row" | "per-row"`.
- Правила:
  - Вход: массив объектов (или один объект = одна строка). Иное — `ok: false` с понятной причиной.
  - Колонки: объединение ключей всех строк в порядке первого появления; отсутствующий ключ → `NULL`.
  - Строка → `'...'`, одинарные кавычки удваиваются.
  - Число → как есть. Известное ограничение: числа за пределами `Number.MAX_SAFE_INTEGER` уже потеряли точность при `JSON.parse` — задокументировать в UI.
  - `true`/`false` → `TRUE`/`FALSE`; `null` → `NULL`.
  - Вложенные объект/массив → JSON-текст как строковый литерал.
  - Идентификаторы (таблица, колонки): без кавычек, если соответствуют `^[A-Za-z_][A-Za-z0-9_]*$`, иначе в двойных кавычках с удвоением `"` внутри.
- Тесты покрывают каждое правило выше + пустой массив + массив примитивов (ошибка).

**Проверка:**
- [ ] `npm run test` — все тесты зелёные; владелец просматривает список тест-кейсов в отчёте.

## 8. Отклонения от спецификации и принятые решения

Журнал расхождений между этим документом и реальным проектом. Всё, что отличается от текста выше, должно быть записано здесь.

1. **Раскладка `src/`.** Весь код расширения лежит в `src/` (`entrypoints/`, `lib/`, `public/`), а не в корне, как в исходной версии раздела 3.1. В `wxt.config.ts` заданы `srcDir: "src"` и `publicDir: "src/public"`. `publicDir` нужен явно: при одном `srcDir` WXT 0.20.27 продолжает искать `public/` в корне (проверено на пробном файле). Пути `lib/...` и `entrypoints/...` в остальных разделах читать как `src/lib/...`, `src/entrypoints/...`. Решение владельца. `fixtures/`, `store/` и конфиги остаются в корне.
2. **Запасной сканер ошибок в `parse.ts`.** Сообщения V8 вида `Unexpected token ']', ... is not valid JSON` не содержат `position N` (проверено на Node 22), поэтому по буквальному тексту 3.2 для `invalid-trailing-comma.json` не было бы строки и столбца, что противоречит проверке Шага 2. Если `position N` есть в сообщении, используется он. Если нет, смещение ищет небольшой строгий сканер JSON; значение по-прежнему даёт только нативный `JSON.parse`. Если и сканер упал (например, на очень глубокой вложенности), возвращается только `message`. Суффикс `(line N column M)` из сообщения V8 удаляется, чтобы не дублировать позицию. Решение владельца. Сканер сверен с `JSON.parse` на 60 000 случайных порч фикстур: расхождений по валидности нет; в 130 из ~34 000 случаев, где позиция есть в сообщении V8, смещение сканера на 1 меньше (во всех просмотренных примерах — ошибки в числах); в таких случаях используется позиция V8.
3. **Фрагмент исходной строки в ошибке.** Показывается не более 60 символов строки по обе стороны от ошибки, обрезанные края помечаются `…`; иначе на минифицированном JSON маркер `^` уходит за экран. В спеке этого нет. Относится к Шагу 2.
4. **Процесс.** Ветки `feature/<name>` на каждый шаг и слияние в `master` по подтверждению (правило 5 в разделе 0). Пуш делает владелец. Коммиты без подписи `Co-Authored-By`. Историю один раз переписывали (`SPEC.md` убирали из репозитория и вернули), хеши первых коммитов от этого изменились.
5. **Окружение разработки.**
   - Брендированный Google Chrome (в том числе Flatpak) не подходит для `npm run dev`: с версии 137 он игнорирует `--load-extension`. Используется Chrome for Testing в `~/tools/chrome-for-testing/`, путь задаётся переменной `CHROME_PATH` (в `~/.bashrc`). Проверка Шага 1 «`npm run dev` открывает Chrome» относится к нему. Подробности в `README.md`.
   - `web-ext.config.ts` в `.gitignore` как личный локальный файл; сейчас не используется.
   - В `package.json` добавлен `postinstall: wxt prepare` (создаёт `.wxt/` и типы). Скрипты из раздела 2 не менялись.
   - `biome.json` исключает `fixtures/invalid-*.json` и `fixtures/large.json` (намеренно битый и огромный JSON), включено использование `.gitignore`.
   - Версии: `wxt ~0.20.27`, `typescript ~5.9`, `@biomejs/biome ^2.5.14`. Для Biome патч-диапазон не фиксировался (спека требует его только для WXT).
6. **Ограничения нативного `JSON.parse`** (принимаются сознательно, точный парсер в бэклоге):
   - числа за пределами точности `double` теряют её уже при разборе: `12345678901234567890` показывается как `12345678901234567000`, `-1.5e10` как `-15000000000`;
   - целочисленные ключи объекта (`"1"`, `"2"`) выводятся в порядке возрастания, а не в порядке исходного текста.
7. **Бэклог.** В раздел 7 добавлен пункт Copy minified.
8. **Шаг 3: решения и отклонения.**
   - `renderResult(text)` (проверка размера, разбор, дерево с тулбаром, ошибка или raw) лежит в `lib/toolbar.ts`, а не в `render.ts`: так viewer и будущий content script получают готовый результат одним вызовом. Переключатель темы — там же (`createThemeSwitch`).
   - Тема: цвета заданы через CSS `light-dark()` и `color-scheme` на элементе с классом `jv-app` (во viewer это `<html>`), выбор хранится в `data-jv-theme`. `light-dark()` работает в Chrome 123+; `minimum_chrome_version` в манифесте не задан. При открытии страницы сначала показывается System, затем применяется сохранённая тема, поэтому у пользователей с сохранённой Light/Dark возможна кратковременная вспышка.
   - Разрешение `storage` добавлено в манифест (по разделу 3.4).
   - Свёрнутый узел показывает `{…}` / `[…]` и `N items` (для объектов и массивов одинаково; для одного элемента `1 item`).
   - **Collapse all оставляет корневой узел открытым**, чтобы верхний уровень оставался виден; в спеке это не уточнено. Реализовано пересборкой дерева (`renderJson(value, false)`), а не переключением `details.open`: закрытие тысяч существующих `<details>` в Chrome растёт квадратично (1 МБ: 24 с, 5 МБ: минуты), а узлы, созданные закрытыми, ничего не стоят. Побочный эффект: Collapse/Expand all сбрасывают ручные состояния узлов (и то и другое приводит к одному и тому же виду).
   - Проверка размера считает UTF-8 байты исходного текста (`Blob`), порог `MAX_RENDER_BYTES` = 10 МБ; такой текст не разбирается вообще.
   - Добавлено сообщение «Too deeply nested to format. Showing raw.» на случай исчерпания стека рекурсией при очень глубокой вложенности (проверено на 20 000 уровнях). В спеке этого нет.
   - Пунктуация по-прежнему выводится отдельными `<span class="jv-punct">`.
   - **Производительность** (Chrome for Testing 153, headless; DOM по ~66 элементов на запись): рендер дерева около 2,5–3,5 с на МБ JSON; 5 МБ ≈ 13–17 с (построение ≈ 3 с, остальное вёрстка и отрисовка; 2,5 млн элементов). Collapse all на 5 МБ ≈ 7 с, Expand all ≈ 15 с. Вкладка в это время не отвечает. Ленивая отрисовка и виртуализация — в бэклоге (раздел 7).
   - **Не проверено:** вставка `fixtures/large.json` (5 МБ) в textarea через буфер обмена дала искажённый текст (переносы строк на позициях ~524 286 и 1 048 575, которых нет в файле), поэтому пункт проверки Шага 3 про `large.json` владельцем не пройден. Отрисовка данных такого размера проверена автоматически (генерация внутри страницы). Причина искажения не установлена (предположительно источник копирования или буфер обмена). Перепроверить на Шаге 5 через `npx serve fixtures`.
   - Подтверждено владельцем: Collapse all не сворачивает корневой узел.
9. **Шаг 4: решения и непроверенное.**
   - Пункт меню `Format selected JSON` (id `format-selected-json`, контекст `selection`) создаётся в `runtime.onInstalled`. Ключ в `storage.session` — `crypto.randomUUID()`. Viewer читает ключ из `?id=`, сразу удаляет и форматирует. После чтения `?id=` остаётся в адресной строке, перезагрузка даёт пустой viewer (как требует спека). В манифест добавлено разрешение `contextMenus` (по разделу 3.4); итого `contextMenus` и `storage`.
   - Обработчик меню без `try/catch`: если `storage.session.set` отклонён (квота 10 МиБ), вкладка просто не откроется. Достижимо только при выделении больше квоты; возможное ограничение `selectionText` самим Chrome не проверено (см. ниже).
   - **Проверено владельцем:** клик по пункту меню работает. `selectionText` не обрезается при выделении более половины `large.json` (то есть минимум ~2,6 МБ); верхний предел не определён. Квота `storage.session` (10 МиБ) остаётся возможным ограничением для выделений больше неё.
   - **Проверено автоматически** (клик по нативному меню в headless не вызвать): логика обработчика (в Node с подменой `browser`), наличие пункта меню в зарегистрированном расширении, весь путь `storage.session` → viewer (валидный JSON, не-JSON, отсутствующий и неизвестный ключ, перезагрузка, юникод, 0,4 МБ).
   - **Производительность на машине владельца** (обычный Chrome, `large.json` 5 МБ): первый рендер 26 с, Collapse all 24 с, Expand all 30 с, сворачивание одного блока до 3 с. Это примерно вдвое медленнее моих замеров в headless (п. 8: 13–17 / 7 / 15 с). Вкладка в это время не отвечает. Для v1 принято как есть; ленивая отрисовка и виртуализация остаются кандидатами в бэклог (решение владельца).
10. **Перед Шагом 5: решения владельца.**
   - Добавить глобальный переключатель автоформата (флаг `autoFormat`, по умолчанию включён) **внутри Шага 5**. Основание: функция, перезаписывающая чужие страницы, должна иметь выключатель на случай бага или конфликта с другим расширением. Для «хочу сырой JSON» остаются Raw на странице и `view-source:`. Размещение: заголовок viewer рядом с темой (без отдельной страницы настроек и нового entrypoint). Новых permissions не требуется. Ограничение «хранится только тема» в разделе 1 расширено на этот флаг.
   - Список сайтов не делается, добавлен в бэклог с пометкой «сначала ресёрч».
   - Предупреждение Chrome о доступе ко всем сайтам (`<all_urls>`) владельца не беспокоит; раздел 3.4 остаётся без изменений.
   - **Открытый вопрос, решение не принято:** автоформат на большой JSON-странице заморозит вкладку без согласия пользователя (замеры владельца: около 5 с на МБ, то есть около 50 с на пороге в 10 МБ; см. п. 9). Варианты: порог согласия (выше ~2 МБ показывать raw и кнопку «Format anyway»), либо ленивая отрисовка. Решить до начала Шага 5.
